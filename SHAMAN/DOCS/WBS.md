## 全体見積り
- 実装: 約 85〜90h（保留分を除く）
- 実機検証: 各フェーズの PR ごとに1記事の E2E（Phase 2 はプロンプトをチャットテストで確定した後の1回だけ）、旧2.1 と Phase 3 の完了後に AIOSEO スコアの変更前後比較（診断値として記録）

## 背景
- **AIOSEO TruSEO スコアが低い。** Sonnet 切替（2026-04-24）後に下がった主因は記事からリンクが消えたこと。ただし切替前の内部リンクは 81 本中 79 本が 404 の捏造（Gemini P4 が検索機能で作った偽 URL）で、AIOSEO はリンクの有無しか見ていなかった。
- **以前から不合格の AIOSEO 項目がある。** ワークフローは AIOSEO の項目を送っていない。メタはテーマ用 `st_description` に書くため、AIOSEO は冒頭の挨拶文を説明文に使う。slug は `article-番号`。P3 がキーワードの空白を助詞に置換するので完全一致しない。画像 alt にキーワードが無い。完全一致の判定は本文の品質より優先しない（実行方針）。
- **生成品質の残課題。** メタ末尾の「（133文字）」混入、P4 の決まり文句（「初心者がやりがちなのが」18回、「具体的には」14回）、P2 見出しの根拠なき表現（「研究データから読み解く」「実証実験に基づく」）。
- **本文品質の主要問題は P3 と P4 に集中している。** P3（Gemini Content）では事実の意味変質、架空の経験・経歴、使えない WEB 検索を前提にした情報補完、入力に無い情報の創作を確認する。P4（Claude Strengthen）では架空体験の追加、不要な h4 の増殖、表・リストの機械的な強制、水増し、定型表現の反復、P3 の意味や事実の変質を確認する。プロンプト案を実機で試すと1回ごとに P1〜P5 の API 費用がかかり、P4 だけで1回 7 分前後かかる。
- **失敗時設計。** 途中で失敗するとキューが「待機中」のまま残り、費用をかけた成果も失われる（v1.3 で次版に保留）。

## 実行方針
- slug は現状の `article-番号` を維持する。Phase 0 の実測で、この版の TruSEO に URL の判定項目が無いと分かったため、日本語 slug の方針を取り下げた（2026-09-14）。
- 公開済み記事の壊れたリンクは、実在する記事や出典に差し替え、無ければリンクを外して文字は残す。内部・外部とも同じ扱い。
- フォーカスキーワードの正規形は、キューの KEYWORD を NFKC 正規化して全角・半角空白を除いた形（例: `アジング秋アジ攻略`）とし、AIOSEO のメタデータ（`keyphrases.focus.keyphrase`）にだけ使う。P2 / P3 / P5 の生成プロンプトに正規形を完全一致で入れる指示は作らない（PR #27 の回帰ガード `SHAMAN/test_phase2_content_quality_guard.py`）。
- TruSEO の配置判定（SEO タイトル、メタ、導入文の最初の段落、h2 か h3、内部リンク、外部リンク。[Phase 0 調査結果](./PHASE0_REPORT.md)）は診断値として記録し、本文生成のルールや再生成の条件にしない。
- AIOSEO 5.0.1.1 では、投稿作成時に `aioseo_meta_data` で title、description、`keyphrases.focus.keyphrase` を同時に保存できる（0.1 で確認済み）。
- WordPress 認証は記事キュー「サイト共通設定」の WP_USER / WP_APP_PASSWORD を使う。
- 公開済み記事の更新は取り消しにくいので、ドライラン、バックアップ、人のレビューを必ず挟む。
- P3 と P4 のプロンプト修正案は、各モデルのチャットで別々に評価して1案に絞る。実機 API は確定案の最終確認に1回だけ使う（Phase 2）。
- PR はフェーズ単位で分け、マージは人が行う。各 PR で Strict TDD 4-Step（pytest、JSON 再生成、Jest、外部 LLM レビュー）を通す。

## Phase 2 P3 / P4 プロンプト品質改善（チャットテスト）

目的: P3 / P4 のプロンプト品質改善案を、実機 API を繰り返し実行せずに評価できるテスト手順を確立し、その手順で修正候補を評価・確定する。

- Phase 2 は従来の AIOSEO 最適化実装を再開するフェーズではない。旧 Phase 2 の項目は、下の「保留・取り下げ 旧 Phase 2」で整理した。
- Phase 2 の主目的は P3 / P4 のプロンプト改善で、品質ゲートなどの実装は変更しない。
- P3（Gemini Content）と P4（Claude Strengthen）はモデルも責務も違うため、同時に修正・評価せず、別々に検証する。
- チャットでの生成は本番と同じモデルで行う。P3 は Gemini のチャット、P4 は Claude のチャット。ChatGPT など別モデルの出力を本番モデル相当とみなさない。
- 修正候補は PR #27 の回帰ガードに従い、正規形のフォーカスキーワードを完全一致で入れる指示を含めない。

**運用制約（非機能要件）**
- 実機 API テストの回数を最小化する。複数案を実 API で試さず、チャットで評価して1案に絞ってから、実機で確認する。
- 実機 API は反復テストの手段にしない。2.11 で不合格なら、原因の工程のチャットテスト（P3 は 2.3〜2.5、P4 は 2.6〜2.8）に戻る。
- 人がチャットへ貼り付けて出力を回収する回数は必要最小限にする。修正候補は原則1案とし、過去の Execution の実出力で比較できるときは、現行プロンプトをチャットで生成し直さない。
- 人の恒常的な保守作業を増やさない。テスト専用 DB、Replay 基盤、fixture 収集基盤、テスト専用 n8n workflow、人による大量のデータ整形、毎回の手動データ登録は前提にしない。既存の Execution から必要な項目だけをコピーして使う。
- 抽出した入力とチャットの出力はリポジトリに保存しない。評価結果は PR 本文に表で残し、採用したプロンプトの検証結果は Phase 1 と同じく `prompts.py` のコメントに残す。

### 比較基準の決め方

- 原則として、過去の Execution の実出力を比較基準にする。P3 は Parse Content 出力の `htmlContent`、P4 は Parse Strengthened Run 1 出力の `articleHtml`（再試行した回は `p4PrevHtml`）を使う。
- 実出力を基準にしてよいのは、当時の `P3_RAW` / `P4_RAW` が現行と同じ場合（Execution の日時と `prompts.py` の変更履歴で確認する）か、違っていても、確認したい問題が実出力に現れていて候補の出力と比べられる場合。
- 現行プロンプトからチャットで基準を生成し直すのは、次のどちらかに当てはまる場合だけにする。
  - 当時と現行のプロンプトが、確認観点に関わる箇所で違う。
  - 候補の出力で問題が減った理由が、プロンプトの差なのか、API とチャットの違いなのか区別できない。
- 実出力（API）と候補の出力（チャット）を比べるときは、生成環境が違うことを評価結果に書き添える。

### チャット環境の条件

| 項目 | P3（Gemini チャット） | P4（Claude チャット） |
|---|---|---|
| モデル | Execution の `geminiModel`（既定は `gemini-3.1-pro-preview`。`GEMINI_MODEL_PRO` で上書きされる） | Execution の `claudeModel`（既定は `claude-sonnet-4-6`。`CLAUDE_MODEL_STRENGTHEN` で上書きされる） |
| ツール | Google 検索（グラウンディング）などのツールを無効にする。本番の P3 リクエストはツール無し。無効にできる環境（例: Google AI Studio）を使う | Web 検索などのツールを無効にする。本番の P4 リクエストはツール無し |
| 生成設定 | 設定できれば温度 0.7（本番と同じ）。システム指示は空にする | 拡張思考をオンにする（本番は adaptive thinking、effort high）。プロジェクト、カスタム指示、スタイル、メモリは使わない |
| 会話の形 | 1通目は「以下の記事構成案をインプットしてください。インプットが完了したら「インプットしました」とだけ返答してください。」と空行の後に `outlineText`。2通目は変数を置換した `P3_RAW`（本番は1通目への応答として「インプットしました」を固定で入れている） | 1通で送る。変数を置換した `P4_RAW` の `### 以下記事本文 ###` の後に空行を1つ入れ、`htmlContent` を続ける |
| 回数 | 候補1案につき1回。追加の生成は、人の作業の表の「必要な場合だけ」に当てはまるときに限る | P3 と同じ。出力が途中で切れた回は、続きを生成させてつながずに無効とする（本番では切れると Parse Strengthened が失敗する） |

- 同じモデルを選べない場合は、別モデルで代替せず、人と扱いを決めてから進める。
- 生成するときは新しいチャットを使い、前の生成を文脈に残さない。
- チャット UI と API は完全には一致しない（UI 側のシステムプロンプトなど）。この差は 2.11 の1回で確認する。

| 除外（機密） | `wpUser`、`wpAppPassword`、`wpUrl` | WordPress の認証情報と接続先 |

### n8n Execution からの取得手順

1. n8n の実行一覧から、P3 と P4 が正常に完了した Execution を開く。実行データは 14 日で削除される（`EXECUTIONS_DATA_MAX_AGE=336`）ので、選んだら削除前に抽出を済ませる。
2. 下の表の対象ノードを開き、入力か出力のパネルと Run を選ぶ。
3. 表の項目の値だけを1項目ずつコピーする。ノードの JSON 全体、Execution 全体、n8n API の `includeData=true` の応答はコピーしない。
4. AI が貼り付け用の文面を組み立て、貼る前に「除外ルール」の検査をする。コピーした値は作業者の手元に置き、リポジトリに保存しない。

| 用途 | 対象ノード | パネル / Run | 取得する項目 |
|---|---|---|---|
| P3 入力 | Build P3 Request | 入力（= Parse Outline の出力） | `KEYWORD`、`SITENAME`、`AUTHOR`、`BASEURL`、`FIRSTPERSON`、`outlineText`、`p1Knowledge` |
| P3 モデル確認 | Build P3 Request | 出力 | `geminiModel` |
| P3 実出力（比較基準の候補） | Parse Content | 出力 | `htmlContent`、`p3LinksRemoved` |
| P4 入力 | Build P4 Request | 入力、Run 1（= Parse Content の出力） | `htmlContent`、`KEYWORD`、`SITENAME`、`AUTHOR`、`FIRSTPERSON`、`p1Knowledge` |
| P4 モデル確認 | Build P4 Request | 出力、Run 1 | `claudeModel` |
| P4 実出力（比較基準の候補） | Parse Strengthened | 出力、Run 1 | `articleHtml`（再試行した回は `p4PrevHtml`） |
| P4 修正方式（任意） | Build P4 Request | 入力、Run 2 | `p4PrevHtml`、`p4QualityFeedback` |

品質ゲートで再試行しなかった Execution では、Build P4 Request と Parse Strengthened は Run 1 だけになる。

### 除外ルール（チャットへ渡さないもの）

| 区分 | 対象 | ある場所 |
|---|---|---|
| API キー | `GOOGLE_AI_API_KEY`、`ANTHROPIC_API_KEY`、`OPENAI_API_KEY` | `.env` と環境変数。Gemini: / Claude: の HTTP Request ノードのエラー詳細に、リクエストヘッダとして出ることがある |

### P4 の確認観点と関係する現行指示

| 確認観点 | 関係する現行指示（`P4_RAW`）と品質ゲート |
|---|---|
| 架空体験の追加 | 4.「${FIRSTPERSON}自身の体験として、うまくいった場面か失敗した場面を1つ…入れてください」 |
| 不要な h4 の増殖 | 1.「疑問を2〜4個想定し、それぞれに答える<h4>小見出しを立ててください」、2.「各<h4>の下は2〜3段落、250〜400文字」 |
| 表・リストの機械的な強制 | 3.「各<h3>セクションに、内容に合うものを必ず1つ以上入れてください」。品質ゲートも、ol / ul / table の無い h3 があると修正方式（API 1回の追加）に回す |
| 冗長化・水増し | 6.「900〜1,300文字を目安」、見直しの「900文字に届かない<h3>セクション」。品質ゲートは h3 本文が 700 文字未満だと修正方式に回す |
| 定型表現の反復 | 決まった書き出しは記事全体でそれぞれ2回まで（1.2 で導入済み。回数を確認する） |
| P3 の意味や事実の変質 | 変えてはいけないのは見出しと導入文だけで、「段落の書き直しや並べ替え…を自由に行ってください」としている |

P4 の候補が表・リストの強制や文字数の目安を外す場合、既存の品質ゲートの条件を満たさない記事では修正方式が走り、API 呼び出しが1回増える。2.6 と 2.10 で矛盾を記録し、ゲートの修正はプロンプト変更とは別のタスク・別の PR で扱う。

### 評価基準

P3（比較基準と候補の出力で同じ確認を行う）

| 評価項目 | 確認方法 |
|---|---|
| 入力に存在しない経験・経歴を創作していない | AI が体験・経歴の記述を抜き出し、入力（`outlineText`、`p1Knowledge`）に無いものを列挙する。人は列挙された箇所だけ確認する |
| WEB 検索不能な状態で、検索したかのような情報を追加していない | AI が入力に無い固有名詞、数値、日付、製品名、「調べたところ」のような記述を列挙する |
| P1 / P2 由来の事実の意味を変えていない | AI が入力の事実と本文の対応を照合し、言い換えで意味が変わった箇所を列挙する |
| 不確実な情報を断定していない | AI が数値、効果、安全に関わる断定を列挙する |
| 構成に従って自然な本文を生成している | 機械的に、h2 / h3 のテキストが `outlineText` と一致すること、導入文直後の ul が4項目であること、`<a>` が0本であることを確認する。自然さは人が通読する |

P4（比較基準と候補の出力で同じ確認を行う）

| 評価項目 | 確認方法 |
|---|---|
| 新しい事実や経験を勝手に追加していない | AI が P3 出力（`htmlContent`）と `p1Knowledge` に無い体験、数値、固有名詞を列挙する |
| P3 の事実関係を変更していない | AI が P3 の記述と対応する箇所を照合し、変わった箇所を列挙する |
| h2 / h3 構造を維持している | 機械的に、見出しのテキスト、順番、数が P3 出力と一致することを確認する（品質ゲートと同じ条件） |
| 不要な h4、表、リスト等を機械的に増殖させていない | 機械的に、h3 ごとの h4、table、ol、ul の数を比較基準と比べる。内容に合わないものは人が確認する |
| 文章量だけを目的に水増ししていない | 機械的に h3 ごとの文字数を比べる。AI が同じ内容の繰り返しや言い換えを列挙する |
| 定型表現を過剰反復していない | 機械的に、`P4_RAW` に挙げた決まった書き出しと、同じ文頭の回数を数える |
| 読者にとって実際に有用な情報が増えている | 人が P3 出力と比べて通読し、理由、具体的なやり方、判断基準が増えたかを確認する |
| 既存の品質ゲートとの整合 | 機械的に、h3 本文 700 文字以上、ol / ul / table あり、追加リンク0本かを確認する。満たさない点は記録し、ゲートの修正が必要なら別タスク・別 PR にする |

- 機械的な確認は、AI が回収した出力に対して作業時に行う。専用ツールはリポジトリに追加しない。
- 採用の条件: 創作、検索前提の補完、事実の変更、見出し構造の項目で、比較基準より悪化した項目が1つでもある案は採用しない。そのうえで、対象の問題が比較基準より減った案を1つ選ぶ。

## 主なリスク
- 0.1 で AIOSEO のフォーカスキーワードを API から設定できない場合、旧2.1 はタイトルとメタのみになり、キーワード系の判定は手作業が残る。

- 4.4 は公開記事を直接更新する。バックアップ、ドライラン、人のレビューを通過したものだけ適用する。
- P4 に候補リンクを渡すと入力トークンと所要時間が増える。現状 P4 は1回 7 分前後。
- チャット UI と API の違い（UI 側のシステムプロンプト、生成設定、思考の扱い）で、チャットの結果が本番で再現しないことがある。実出力を比較基準にした場合は、差の一部が生成環境によるものになる。2.11 の1回で確認し、再現しなければ API で調整を繰り返さず、チャットテストに戻る。
- n8n の実行データは 14 日で削除される。2.1 で選んだ Execution は、削除前に 2.2 の抽出を済ませる。
- P4 の候補が表・リストの強制や文字数の目安を外すと、既存の品質ゲートと矛盾し、ゲートを直すまで修正方式の API 呼び出しが増える。2.6 と 2.10 で記録し、ゲートの修正はプロンプト変更とは別のタスク・別の PR で扱う。

## 検証方法
- 各フェーズ: 先に失敗するテストを書き（pytest / Jest）、JSON 再生成後に両方全緑、外部 LLM レビュー【問題なし】。
- P3 / P4 のプロンプト変更（Phase 2）: 修正案はチャットテストで1案に絞る。組み込んだプロンプトがチャットで評価した文面と一致すること、既存の品質ゲートとの整合を確認してから、実機で1回だけ確認する（2.10、2.11）。
- その他のプロンプト変更（1.2、1.3、3.2、3.5）: 保存済みの実行データでオフライン検証し、組み込んだプロンプトが検証時と一致することを照合する。
- 旧2.1・Phase 3: 実機で1記事を下書き投稿し、WordPress 編集画面の TruSEO スコアとチェック項目を変更前の記事と比較し、診断値として記録する。リンク先は全件 HTTP で確認する。
- Phase 4: ドライランの差分を人が確認してから本番更新し、再監査で壊れたリンク 0 本を確認する。
- Phase 5: 実機でキー無効、参照画像空、アップロード失敗を起こし、キューのステータス、再開位置、Discord 通知を確認する。
