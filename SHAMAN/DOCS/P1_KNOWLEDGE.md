# P1 のナレッジを根拠にした記事づくり（ハルシネーション対策）

2026-11-09。オーナーの改修指示「ハルシネーション対策とLLMモデル配置の最適化」による。

## 1. 目的

記事の品質（文字数・見出しの構成・情報量・文体）を保ったまま、根拠の無い情報を記事に入れない。

改修前は、次の食い違いがあった。

- P2・P3 には検索の機能が無いのに、プロンプトが「WEB 検索したときに出てくる関連キーワードを取得し」「不足する情報は自律的に WEB で情報を収集し」と指示していた。モデルは検索できないので、自分の知識で埋めるしかない。
- P3 は「記事内のすべての記述は、あなた自身の知識、経験、見解に基づくものとして」「参考ナレッジを、あなた自身の実際の経験・専門知識として完全に同化させ」と指示していた。ペルソナの語り口と、実体験を作ることの区別が無かった。
- P4 は「${FIRSTPERSON}自身の体験として、うまくいった場面か失敗した場面を1つ」入れるよう指示していた。実体験は渡していない。
- P4 は、数値や製品名を「一般に広く知られている内容」からも書いてよいとしていた。

## 3. P1 のナレッジ

### 3.1 見出し

`prompts.P1_PROMPT` は、次の 5 つの見出しで整理させる。

| 見出し | 中身 |
|---|---|
| `## メインキーワードと検索意図` | 検索する人の悩みと目的 |
| `## 関連キーワード` | 検索したときに出てくる関連キーワード（1 行に 1 つ）。P2 の H3 と P3 の導入文は、ここから選ぶ |
| `## 記事に使える具体的な事実` | 検索で確かめた事実 |
| `## 数値・製品仕様・固有名詞` | 検索で確かめた数値、製品名と仕様、メーカー名、地名など |
| `## 確認できなかった情報` | 検索で確かめられなかったこと。無ければ「なし」 |

確かめられなかった数値・仕様・固有名詞は、推測や一般論で埋めずに「確認できなかった情報」に書かせる。P2〜P4 のプロンプトは、ここに挙げられた内容を推測で補わないよう指示する。

### 3.2 情報源（URL）と確認日

モデルには URL を書かせない。書かせると、実在しない URL を作ることがある。

`Parse Research` が、応答の `groundingMetadata`（Google 検索で実際に参照したページ）から次を取り、`p1Sources` に入れる。

| 項目 | 元のデータ |
|---|---|
| `checkedAt`（確認日） | P1 を実行した日時 |
| `queries` | `webSearchQueries`（モデルが検索した語） |
| `sources`（番号・サイト名・URL） | `groundingChunks[].web`（`title`・`uri`） |
| `supports`（どの文がどの情報源に基づくか） | `groundingSupports[]`（`segment.text`・`groundingChunkIndices`） |

- `p1Sources` は内部のデータ。記事には載せない。プロンプト評価では「評価データ」に、本番では n8n の実行データに残る。
- P2〜P4 に渡すナレッジ（`p1Knowledge`）の末尾には、「情報源（Google 検索で参照したサイト。確認日 YYYY-MM-DD）」として**サイト名だけ**を書く。URL を渡すと、リンクを作る材料になるため。

### 3.3 調査が足りないとき

次のときは `p1ResearchStatus` に残す。記事の処理は止めない。

| 状態 | 文 |
|---|---|
| 検索の情報源が 1 件も無い（検索をしなかった・結果が無かった） | `P1: Google 検索の情報源がありません（追加の調査が必要）`。ナレッジの情報源の欄にも「このナレッジの事実は確認されていません」と書く |
| 「確認できなかった情報」に中身がある（「なし」「特になし」だけなら、無いとみなす） | `P1: 検索で確認できなかった情報があります（追加の調査が必要）`。中身は `p1ResearchGaps` |

`p1ResearchStatus` は、キュー（「SHAMAN本番用」スプレッドシートの「記事キュー」シート）のエラー内容の列と、Discord の完了の通知に出る。STATUS は変えない（記事は下書きで投稿される）。

## 4. 記事の外を指す書き方（内部リンク対策）

実在を確かめたリンクはまだ無い（既存の記事の取得・関連記事の推薦は、将来の ARBW 連携で行う）。そのため、記事の外を指す書き方は記事に残さない。

| 対象 | P3 | P4 |
|---|---|---|
| リンク（`<a>` タグ） | プロンプトで禁止。`Parse Content` が外して文字だけ残す（前から） | プロンプトで禁止。品質の確認で、下書きに無いリンクを指摘する（前から）。最後に、残ったリンクをすべて外して文字だけ残す（`p4LinksRemoved`） |
| 本文の URL の文字列（`http(s)://`・`www.` で始まるもの） | プロンプトで禁止 | 品質の確認で指摘する。最後に消す（`p4UrlsRemoved`）。タグの属性の値は変えない |
| 自サイトの他の記事への言及（「別の記事」「関連記事」「あわせて読みたい」「過去の記事」「当サイトの記事」など。「この記事」は今の記事なので対象にしない） | プロンプトで禁止 | 品質の確認で指摘する |

- 品質の確認（`Parse Strengthened`）の指摘は、1 回目なら作り直しの呼び出しで直してもらう（P4 の呼び出しは前と同じく最大 2 回）。
- **2 回呼んでも、選ばれた稿に自サイトの記事への言及が残っていれば、記事として採用しない**（PR #85 レビュー B1）。`Parse Strengthened` が `SHAMAN_RUN_NG: P4 を 2 回呼んでも、自サイトの他の記事への言及が N 箇所残っています（…）` で止まり、WordPress には投稿しない。言及は文の一部なので、機械では消さない。
  - 本番では、n8n の実行が Error で終わり、Discord にエラーが届く。キューの行は、今の P1〜P5 の失敗と同じく「処理中」のまま残る（行を「エラー」にして次の行へ進む改修は、別に行う）。
  - プロンプト評価では、その回のエラーの結果になる（`Eval: Parse Failed`）。
- リンクと URL の文字列は、文の意味を変えずに外せるので、止めずに外して進む。
- 見つける語は `generate_workflows.py` の `ARTICLE_REF_JS`。

## 5. P6A：画像を入れる見出し

- 選ぶ箇所は 5〜7（前から。5 未満なら `insufficient_sections_N`、8 以上なら最初の 7 つ）。
- `insertionContext` が、記事に実在する見出し（h2〜h4）の文字と同じでなければ、その節を使わない（`Parse Section Plan`）。空白の数の違いだけは同じとみなす。同じ見出しを 2 回選んだら、2 回目は使わない。外した数は `p6SectionsDropped`。

- JSON の形と scene の項目は変えない。

## 7.3 実際の API での 1 回目の結果と、直したこと（2026-11-09）

KEYWORD「アジング コツ 夜」で、P1（R17-1）→ P2（R18-1）→ P3（R20-1）→ P4（R21-1）→ P6A（R22-1）を動かした。測定値はすべて条件を満たした。しかし、本文を P1 のナレッジと照らし合わせたところ、**ナレッジに無い具体的な説明が記事に入っていた**（オーナーのレビュー）。

- 例：発光体について「光の止まり方や動き方でアタリを目視できる」「アジが吸い込むと光が横にずれたり沈んだりする」。ナレッジで確かめられているのは、仕掛けの位置を把握する用途まで。
- P3（R20-1）がこの説明を作り、P4（R21-1）が詳しくした。

原因と直したこと：

| 原因 | 直したこと |
|---|---|
| P4 のプロンプトが「【参考ナレッジ】と**下書き**に書かれているもの」を根拠にしてよいとしていた。P3 が作った説明が、そのまま根拠になる | P4 の根拠は【参考ナレッジ】だけにした。下書きにあってもナレッジに無い具体的な事実は、ナレッジの範囲に書き直すか削除し、その分はナレッジの事実を詳しく説明して補う。作り直しの呼び出しも同じ。「導入文と 4 項目のリストを変えない」（1 回目）、「指摘のないセクションと導入文は一字一句変えない」「足すことだけ」（作り直し）より、この訂正を優先する（PR #88 レビュー）。見出しは変えない |
| 制限の対象が「数値・製品仕様・固有名詞」だけだった。やり方・効果・見分け方（「〜すると〜が分かる」）は制限していなかった | P3・P4 で、具体的な事実に「やり方の手順、道具や操作の効果、見分け方、魚の反応」を含めた |
| P3 に「理由・仕組みの論理的な解説は書いて構いません」と広く許していた。ナレッジからの推測で、新しい効果や見分け方を足せた | 許すのは「ナレッジの事実どうしをつなぐ説明」と「ナレッジの理由・仕組みの言い換え」だけにした。新しい効果・見分け方・手順・現象を推測で足さない |
| ナレッジが記事に対して少なすぎた。P1 の出力は 1,093 トークン、記事は 12,567 文字。h4 ごとに具体的なやり方を書かせるので、足りない分をモデルが補う。前の P1 のプロンプトでは 1,994 トークンだった（R6-1、別の KEYWORD。比べられるのは 1 回ずつ） | P1 に、このナレッジだけで 12,000 文字程度の記事を書くことを伝えた。「記事に使える具体的な事実」を論点（基本、手順、判断の基準と理由、道具、効果、失敗と直し方）ごとに「### 」で分け、検索で確かめた内容を具体的に書かせる |

ナレッジに無い説明を足さないようにすると、記事が短くなるおそれがある。そのため、P1 のナレッジを増やすことと組で直した。直した後に、同じ KEYWORD で P1〜P4 をもう一度動かし、ナレッジの文字数・記事の文字数・本文の照らし合わせを、前の結果（R17-1・R21-1）と比べる。

## 7.5 本番で情報源が 0 件だった（2026-11-10）

本番の実行 43（「SHAMAN本番用」「記事キュー」31 行目、KEYWORD「アジング コツ 夜」、投稿 ID 1906）で、P1 の情報源が 0 件のまま記事が投稿された（「P1: Google 検索の情報源がありません（追加の調査が必要）」）。

- 原因：`Gemini: Research` の応答に `groundingMetadata` が無かった。Google 検索をせず、モデルの知識だけで答えた（検索するかどうかはモデルが決める）。同じ KEYWORD の評価（R26-1）では 32 件あった。API の使用量（`usageMetadata`）には検索の有無が出ないので、使用量からは見分けられない。
- 検索しなかったナレッジには、確かめられていない内容が入っていた：「尺アジが釣れやすいという科学的な研究データがある」、釣り人の実名、具体的な漁港名、検索していないのに「確認できなかった情報」に挙がった語。投稿 ID 1906 の下書きは、このナレッジで書かれている。
- 直したこと：`Parse Research` が、1 回目で情報源が 0 件なら、ナレッジを作らずに `P1: Retry?` で `Build P1 Request` に戻す（1 回だけ）。**2 回目も 0 件なら `SHAMAN_RUN_NG` で止め、記事を作らない**（オーナーの判断、2026-11-10）。止まった行は、Actions の `recover_execution` でやり直せる（DOCS/RUN_FROM_ACTIONS.md）。評価も同じ。

## 8. 残る制約
