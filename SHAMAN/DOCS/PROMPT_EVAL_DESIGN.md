# SHAMAN プロンプト評価 Workflow 設計書

（2026-11-04 作成。2026-11-04 にオーナーが承認）

## 1. 目的

LLM のモデルやプロンプトを変えたときの影響と、出力の品質を、**ステップごとに**評価する。

- Workflow 全体が最後まで流れるかは試さない（本番で流れることは確認済み）。キューの確保・書き戻し、WordPress、Discord、途中保存は試験の対象にしない。
- 外部サービスにつながるかは、接続確認 Workflow（`CONNECTION_CHECK.md`）で確かめる。
- この Workflow は、前の Test Workflow（DRY_RUN・SKIP_IMAGE・自動 DRY_RUN）に置き換わる。

## 2. 要件

1. **各ステップを単独で実行できる。** 1 回の実行で 1 つのステップだけを動かす。
2. **LLM のモデルやプロンプトを変えたときに、各プロンプトの出力を評価できる。** 同じ入力で、モデルやプロンプトだけを替えて比べる。
3. **各ステップの出力データを再利用できる。** 出力は項目ごとに全文を残し、別のステップの入力や、別の評価の比較の基準に、何度でも使える（§4.3）。
4. **各試験がログを残す。** 送ったリクエスト、受け取った応答、エラー、所要時間を、実行の記録とは別に残す（実行の記録は 14 日で消える）（§4.6）。

### 過去の失敗から決めたこと

| 過去の失敗 | 要件 |
|---|---|
| プロンプトの案を 1 つ試すたびに P1〜P5 の API 費用がかかり、P4 だけで約 7 分かかった（WBS 背景） | 1 回の実行では 1 つのステップだけを動かす。入力は固定し、前のステップを流し直さない |
| 実行の記録は 14 日で消える。記録には認証情報（`siteConfig` など）も入っていた（WBS 2.2） | 入力と出力は、試験用のスプレッドシートに残す。認証情報の項目は持たない |
| P3 と P4 を一緒に試すと、どちらの原因かわからない（WBS Phase 2） | ステップごとに独立して評価する。入力には、決めておいた出力（§4.3）だけを使う |
| P4 を作り直したら、11,940 字が 8,393 字に縮んだ（実行 1293） | 出力は、比較の基準と同じ測定値（文字数・h3・h4・表・リストの数）で並べる |
| P3 が偽の内部リンクを 3 本作り、すべて 404 だった（1295）。Gemini の P4 では、81 本中 79 本が捏造だった | 出力のリンクを数え、入力にない URL を抜き出す |
| メタの説明文の末尾に「（133文字）」が入った（1294） | P5 の出力で、文字数と末尾の注記を確かめる |
| P2 の見出しに「研究データが示す…」が入った（5 回中 5 回）。条件を厳しくすると、守れた割合が 3/5 から 0/5 に下がった | 同じ入力で N 回実行し、守れた割合で評価する |
| Sonnet に替えたあと、記事からリンクが消えて AIOSEO の点が下がったが、すぐには気づかなかった | モデルを替えるときは、本番に入れる前に、プロンプトごとに旧モデルの出力と比べる |
| Sonnet 5 は、既定以外の `temperature` を送ると 400 を返す | API のエラー・`stop_reason`（`max_tokens`・`refusal`）を、実行ごとに結果に残す |
| 自動 DRY_RUN は大掛かりだったが、設定を読み込めるかしか確かめていなかった（#62・#63） | 自動 DRY_RUN・DRY_RUN・SKIP_IMAGE はやめる |

## 3. 範囲

| ステップ | 使うノード（本番と同じ組み立て関数） | モデル |
|---|---|---|
| P1 Research | Build P1 Request → Gemini: Research → Parse Research | `MODEL_PRO` |
| P2 Outline（2 ターン） | Build P2 Request → Gemini: Generate Outline → Parse Outline | `MODEL_OUTLINE`（2026-11-09 から gemini-3.5-flash-lite） |
| P3 Content | Build P3 Request → Gemini: Generate Content → Parse Content | `MODEL_PRO` |
| P4 Strengthen | Build P4 Request → Claude: Strengthen Content → Parse Strengthened（品質ゲートの作り直しを含む） | `MODEL_CLAUDE` |
| P5 Meta | Build P5 Request → Gemini: Generate Meta → Parse Meta + Extract Title | `MODEL_FLASH_LITE` |
| P6 節の分析 | Build Section Analysis Request → … → Parse Section Plan | `MODEL_SECTION_ANALYSIS`（2026-11-09 から gemini-3.8-flash） |
| P6 画像（1 枚） | Check P6 Mode（評価の代わりのノード）→ 参考画像を Google Drive から読む（本番と同じノード）→ Eval: P6 Section → Build Image Requests → P6: Generate Image → Collect Generated Images | `MODEL_IMAGE_OPENAI` |

- プロンプトと解析の処理は、本番と同じ組み立て関数から作る（`generate_workflows.py` の各ステップを関数に分け、本番と評価の両方で使う）。評価のために別のプロンプトや別の解析を書かない。
- **P6 画像**（2026-11-09 に追加。[P6_IMAGE_REQUEST.md](P6_IMAGE_REQUEST.md)）：入力は P6A の結果 ID。費用を抑えるため、P6A の結果の**最初の節だけ**、画像を 1 枚作る（本番は 5〜7 枚）。参考画像は、本番と同じく入力の `imgFolder` のフォルダーから読む。作り直し（429・5xx）はしない。
  - 評価データには、画像そのもの（base64）を残さず、長さ（`imageB64Chars`）とエラーを残す。評価ログのリクエストと応答も、参考画像の data: URL と生成した画像は長さだけを残す。トークン数（応答の `usage`）は残す。
  - この Workflow が Google Drive を使うのは、参考画像を探す・ダウンロードするときだけ。OpenAI を使うのは `P6: Generate Image` だけ（配備のスクリプトが確かめる）。

## 4. 構成

### 4.1 Workflow

| 項目 | 値 |
|---|---|
| 名前 | `SHAMAN: Prompt Eval` |
| ID | `shaman_test`（前の Test Workflow の ID を引き継ぐ。配備のスクリプトは、前の名前 `SHAMAN: Test Workflow` の Workflow を、同じ ID のまま新しい名前で上書きする） |
| 生成元 | `SHAMAN/prompt_eval.py`（`generate_workflows.py` を実行すると、一緒に生成される） |
| 生成物 | `SHAMAN/workflows/SHAMAN_Prompt_Eval.json` |
| 起動 | Actions の「SHAMAN | n8n Workflow実行」で `test` を選ぶ（合言葉付きの Webhook `shaman-prompt-eval`。公開して配備する。[RUN_FROM_ACTIONS.md](RUN_FROM_ACTIONS.md)）。n8n の画面の Manual Trigger からも実行できる |
| 書き込み先 | 試験用のスプレッドシートだけ（本番のシート・WordPress・Discord には書かない） |

### 4.2 試験用スプレッドシートのシート

| シート | 書く人 | 中身 |
|---|---|---|
| 評価の実行 | Workflow（Actions の入力から行を足す。画面から実行するときはオーナーが書く。状態と結果の列は Workflow） | 1 行が 1 回の評価。実行キー、ステップ、入力、モデル、回数、状態 |
| 評価結果 | Workflow | 1 回の生成ごとに 1 行。結果 ID、測定値、モデル、プロンプトの版、入力に使った結果 ID、エラー |
| 評価データ | Workflow | 出力の本文。結果 ID・項目名（`outlineText`・`htmlContent`・`articleHtml` など）・分割番号・本文 |
| 評価ログ | Workflow | 試験のログ（§4.6） |

- キューのシートとは別のシートにする。キューの行は読まない。
- 1 つのセルには 50,000 文字までしか入らない。それより長い本文は、45,000 文字ずつに分け、分割番号を付けて複数の行に書く。読むときは、分割番号の順につなぐ。切り詰めない。

### 4.3 入力

ステップの入力は、「評価の実行」の行で指定する。

- **P1**：キーワードとサイトの設定（KEYWORD、OPTION1、SITE_ID）を行に書く。サイトの設定は `sites.json` から読み、本番の Map Variables で、ほかのステップと同じ項目にする。SITE_ID が `sites.json` にないと止める（今の `sites.json` は空なので、P1 を評価するには、先にサイトを足す）。
- **P2 以降**：「評価結果」の **結果 ID** を書く。その結果の出力（「評価データ」の本文）が、そのステップの入力になる（P3 なら、P2 の結果の `outlineText` と、その P2 が入力に使った P1 の結果の `p1Knowledge`）。
- **本番の実行から（P2〜P5）**：Actions の `eval_input_execution` に本番の n8n の実行 ID を書くと、その実行で、そのステップの Build ノードが受け取ったデータ（P2：Parse Research、P3：Parse Outline、P4：Parse Content、P5：P4: Retry? の 2 つ目の出力）を入力にする。本番が途中で止まったとき、止まったステップだけを、同じ入力で試すために使う（2026-11-07、実行 8 の P4 の時間切れ）。
  - 実行のデータは、Actions のスクリプト（`run_shaman_workflow.py`）が n8n の API（`N8N_DEPLOY_API_KEY`）で読み、Webhook の本文で渡す。本番の Workflow の実行でなければ、またはそのノードの出力が残っていなければ止める。
  - Workflow は、取り込んだデータを「評価データ」に結果 ID `R<この実行の ID>-0` で書いてから（`Eval: Import Rows`・`Eval: Save Import`）、それを入力の結果 ID にする。あとは結果 ID を書いたときと同じ。同じ ID を、次からは `eval_input_id` に書いて何度でも使える。`_meta` の `source` に、取り込んだ実行とノードを残す。
  - 名前が認証の値らしい項目（token・secret・password・api key・webhook など）は書かない。
  - `eval_input_id` と一緒には使えない。
  - **P2 の呼び出しは、1 回の評価（回数 1）で最大 2 回**になる。本番と同じ見出しの確認（`Parse Outline` → `P2: Retry?`）で、1 回目の構成案が見出しの条件（H2 が 2 個、H2 と H3 の合計が 12〜13 個、記号を除いて 25 文字以内、見出しに使えない語が無い）を満たさなければ、満たしていない条件を伝えて 1 回だけ出し直してもらう。2 回目も満たさなければ、その回はエラー（`SHAMAN_RUN_NG: P2 を 2 回呼んでも…`）になる。測定値の `attempts` が呼び出した回数、`firstIssues` が 1 回目に満たしていなかった条件。評価ログの `呼び出し` は、P2 でも何回目の呼び出しか（1 か 2）を残し、トークン数は呼び出しごとの行に残る。評価結果の `API呼び出し回数` も P2 を呼んだ回数になる。
  - 1 つの実行の中で何度も動くノード（回の数、P2・P4 の出し直し）は、`$('ノード名').first(出力, -1)` で最後の実行を明示して読む。runIndex を省いたときの扱いは、n8n のドキュメントでは最初の実行、n8n 2.35.7 のソース（`workflow-data-proxy.ts` の `defaultReturnRunIndex = -1`）では最後の実行で、食い違う。luna では、評価の回ごとに違う結果 ID と測定値が残っており（R30-1〜3）、ソースのとおり最後の実行が返っている。それでも省略には頼らない（PR #89 レビュー B1・B3）。テストのモックは、省くと最初の実行を返す（厳しい側）。
  - **P4 の API 呼び出しは、1 回の評価（回数 1）で最大 2 回**になる。本番と同じ品質ゲート（`Parse Strengthened` → `P4: Retry?`）で、1 回目の出力に問題があれば、その部分だけを直す呼び出しを 1 回だけする（2 回目のあとは作り直さない）。本番の失敗を再現するための試験なので、作り直しは外さない（本番は 2 回目の呼び出しで時間切れになることもある）。費用は、P4 の呼び出し 2 回分までを見込む。呼び出した回数は、評価結果の `API呼び出し回数` と評価ログの `呼び出し` に残る。
- 各ステップの出力は、Parse ノードが次のステップに渡す項目を、すべて「評価データ」に残す。次のステップが必要とする項目がそろっていない結果 ID を指定したら、API を呼ばずに止める。
- そのため、評価の入力は、この Workflow 自身の出力から作れる。実行の記録から手でコピーしなくてよい。同じ結果 ID を何度でも入力にできるので、モデルやプロンプトを替えても、入力は同じに保たれる。
- 比較の基準も結果 ID で指す。「評価の実行」の行に基準の結果 ID を書けば、測定値を基準と並べて評価結果に書く。
- 入力と基準に使った結果 ID は、評価結果の行に残す。結果は消さない（上書きもしない）。

### 4.4 モデルとプロンプトの版

- モデルの列が空なら、本番の定数（`MODEL_PRO` など）を使う。書いてあれば、そのモデルで実行する（英小文字・数字・`.`・`-` だけ。ほかの文字は止める）。
- プロンプトは、配備した版の `prompts.py` を使う。プロンプトを替えて評価するときは、`prompts.py` を変えた PR をマージして配備する（UI で書き換えない）。
- 評価結果には、使ったプロンプトのハッシュ（生成のときに計算して埋め込む）を残す。同じハッシュどうしなら、同じプロンプトで比べている。

### 4.5 回数

- 回数（N）は 1〜5。同じ入力で N 回生成し、それぞれを評価結果の 1 行にする。
- 費用の上限として、1 回の実行で動かすのは 1 行・1 ステップだけ。

### 4.6 ログ

「評価ログ」に、1 回の API 呼び出しごとに残す。失敗した呼び出しも残す。

| 項目 | 中身 |
|---|---|
| n8n の実行 ID・実行キー・結果 ID・回（N 回のうち何回目か、P4 の作り直しは別の回） | どの試験のどの呼び出しか |
| 日時・所要時間 | |
| ステップ・モデル・プロンプトのハッシュ | |
| リクエストの本文 | 置き換え後のプロンプトを含む、送った本文の全文（認証の情報はヘッダーにあり、本文には入らない） |
| 応答の本文 | 受け取った本文の全文（エラーの応答も） |
| HTTP の状態・エラー文・`stop_reason` / `finishReason`・トークン数 | |

- 実行の始めと終わりにも 1 行ずつ残す（「評価の実行」の行の内容、止めた理由、書いた結果 ID の一覧）。API を呼ぶ前に止めたときも残す。
- 本文が長いときは、評価データと同じく分割番号で分ける。
- 認証の情報は残さない。認証は Credential がヘッダーに付けるので、リクエストの本文には入らない。応答のヘッダーは残さない。
- 成功の応答の本文は、出力そのものなので、そのまま残す。エラー文とエラーの応答の本文だけ、API キーらしき文字列（`key=…`、`x-goog-api-key`・`x-api-key`・`Authorization` の値、`AIza…`、`sk-…`）を伏せる。エラーのオブジェクトは、そのまま文字列にしない（リクエストの設定が入りうるため、メッセージなどの項目だけを書く）。
- エラー文の列は 2,000 文字までにする（エラー文は出力ではない。応答の全文は応答の列に分割して残る）。
- 出力のデータ（評価データ）は伏せず、切り詰めない。

## 5. 測定値

測定は Code ノードで行い、評価結果の列に書く。

| ステップ | 測定値 |
|---|---|
| 共通 | 出力の文字数、所要時間、HTTP の状態、API のエラー、`stop_reason` / `finishReason`、トークン数（応答にあれば） |
| P1 | 文字数、見出しの数、検索の情報源・検索語・根拠の対応の数（`sources`・`queries`・`supports`）、ナレッジの 5 つの見出しのうち無いもの（`missingSections`）、「確認できなかった情報」の文字数、調査の状態（`researchStatus`）、本文の URL の数（[P1_KNOWLEDGE.md](P1_KNOWLEDGE.md)） |
| P2 | 見出しの数（h2・h3）、禁止語（研究・実験・実証・検証・調査・分析・データ・科学・統計）を含む見出し、キーワード全体を含む見出しの数、25 文字を超える見出し（`overLength`） |
| P3 | h2・h3 の数、リンクの数（`p3LinksRemoved`）、自サイトの他の記事への言及（`siteRefs`）、本文の URL の数 |
| P4 | 品質ゲートの結果（`p4QualityIssues`）、作り直しの有無、h3 ごとの文字数と h4・table・ol・ul の数、決まり文句の回数、P3 になかったリンク（モデルの生の応答で数える）、P3 と見出しが一致するか、自サイトの他の記事への言及、外したリンクと URL の数 |
| P5 | 文字数、末尾の文字数の注記の有無 |
| P6 節の分析 | 節の数、JSON として読めたか、scene の項目がそろっているか、記事に無い見出しを選んで外した節の数（`dropped`）、見出しタグと一字一句同じだった節の数（`exactContext`） |

- 入力にない事実や経験の創作、事実の意味の変質は、測定値では判定しない。出力を、WBS の「評価基準」の手順で、AI と人が確かめる。
- 比べるときは、評価結果をステップ・入力の結果 ID・モデル・プロンプトのハッシュで絞り込む。

## 6. 安全

- 書き込むのは、試験用のスプレッドシートの「評価の実行」の状態の列と、「評価結果」「評価データ」「評価ログ」だけ。
- 認証は、本番と同じ Credential を使う。API キーはノードにも `$env` にも書かない。
- 「評価の実行」の待機中の行が 1 件でなければ（0 件・複数件）、API を呼ばずに止める（止めたことはログに残す）。

## 7. 外すもの

- 今の Test Workflow の DRY_RUN・SKIP_IMAGE・`TEST_MODE Gate`。
- 自動 DRY_RUN：`verify_shaman_dryrun.py` とその試験、配備の手順（Webhook での実行、`e2e-recovery` のジョブ）、`SHAMAN_E2E_READY`。
- 試験専用のサイト設定 `sites.test.json`。
- 接続確認が使う予約行（`__SHAMAN_AUTO_E2E__`）は残す。

## 8. 決めていないこと

- 本番の公開の条件 `SHAMAN_E2E_PASSED_SHA` は、2026-11-06 に無くした。本番も公開して配備し、Actions から実行する（[RUN_FROM_ACTIONS.md](RUN_FROM_ACTIONS.md)）。
- P4 を N 回続けると、1 回の実行が 30 分を超えることがある。n8n の実行時間の上限を確かめ、超えるなら N の上限を下げる。
- 本番の Workflow を、評価の結果に基づいて替える手順（どの測定値なら採用するか）は、WBS の「評価基準」に従う。この Workflow では決めない。

## 9. 実装

| ノード | すること |
|---|---|
| `Eval: Read Runs` → `Eval: Pick Run` → `Eval: Run OK?` | 「評価の実行」の待機中の 1 行を選び、ステップ・回数・モデル・結果 ID の形を確かめる |
| `Eval: Claim Run` → `Eval: Log Start` | 行の状態を「処理中」にし、開始のログを書く |
| `Eval: Read Input` → `Eval: Read Baseline` → `Eval: Prepare Input` → `Eval: Input OK?` | 入力の結果 ID の評価データを読み、分割をつないで元に戻す（分割の欠け・文字数の違い・失敗した結果は止める）。基準の測定値を読む |
| `Eval: Repeat` | N 回くり返す |
| （P1 だけ）`Map Variables` → `Eval: Apply Model` | 保存したときのモデル名と P4 の途中の状態を消し、今の本番のモデルか、指定のモデルにする |
| `Eval: Route Step` → `Build …`（本番） → `Eval: Stamp` → `Eval: Route Call` → API（本番） | 本番のノードで、リクエストを作って送る |
| `Eval: Call Log Rows` → `Eval: Log Call` → `Eval: Response` | 呼び出しのログを書いてから、本番の Parse が受け取る形（応答の本文）に戻す |
| `Eval: Route Parse` → `Parse …`（本番）（P4 は `P4: Retry?` で作り直しを含む） | 本番のノードで、出力を読む。失敗は `Eval: Parse Failed` へ |
| `Eval: Record` → `Eval: Save Data` → `Eval: Save Result` | 測定値を計算し、出力の全文を評価データに、結果を評価結果に書く |
| `Eval: Finish` → `Eval: Mark Done` → `Eval: Log End` | 行を「完了」か「エラーあり」にし、結果 ID の一覧を書き、終わりのログを書く |
| `Eval: Mark Failed` → `Eval: Log Stop` → `Eval: Stop` | 止めるとき：行を「エラー」にし（確保した後だけ）、止めた理由をログに書いて、実行を失敗にする |

- API のノードは、本番と同じ設定に、応答の全体（状態コード）を受け取る設定と、エラーでも次へ進む設定だけを足す。Parse のノードは、失敗をエラーの出力へ流す設定だけを足す。どちらも、本番の組み立て関数で作る。
- 回の途中のノード（本番の Build、`Map Variables`、`Eval: Apply Model`・`Eval: Stamp`・`Eval: Call Log Rows`・`Eval: Response`）と Parse が失敗したら、その回をエラーの結果（状態「エラー」）にして、次の回へ進む。
- Google Sheets のノードは、失敗したら 5 秒待って、3 回まで試す（429・5xx に備える）。
- 結果 ID は `R<n8n の実行 ID>-<回>`。
- 評価データの `_meta` の項目に、状態・ステップ・モデル・プロンプトのハッシュ・処理のハッシュ（Build と Parse のコード）・入力の結果 ID を残す。

## 10. 準備と実行

### 10.1 シートの準備（Workflow が自分でする）

オーナーが準備することは無い。Workflow は、起動するたびに最初に次のことをする（2026-11-06）。

- `Eval: Ensure Sheets`：試験用スプレッドシートに、次の 4 つのシートが無ければ作る（Google Sheets の「シートを作る」。同じ名前のシートがあれば作らない）。
- `Eval: Sheets Ready`・`Eval: New …?`・`Eval: Header …`・`Eval: Header … Write`：**この実行で作ったシートにだけ**、1 行目に見出しを書く（`autoMapInputData` の追加。空のシートなら項目名を 1 行目に書く）。前からあるシートには、何も書かない。
- 見出しは、この順でなくてもよいが、名前は一字一句同じにする。前からあるシートの見出しが足りなければ、そのシートに書くノードが失敗し、実行は Error で終わる（黙って直さない）。

| シート | 1 行目の見出し |
|---|---|
| 評価の実行 | `実行キー`・`ステップ`・`入力の結果ID`・`基準の結果ID`・`KEYWORD`・`OPTION1`・`SITE_ID`・`モデル`・`回数`・`状態`・`実行ID`・`結果ID`・`メモ` |
| 評価結果 | `結果ID`・`実行キー`・`実行ID`・`日時`・`ステップ`・`回`・`モデル`・`プロンプトのハッシュ`・`処理のハッシュ`・`入力の結果ID`・`基準の結果ID`・`状態`・`エラー`・`API呼び出し回数`・`出力の文字数`・`測定値`・`基準の測定値` |
| 評価データ | `結果ID`・`項目`・`型`・`分割番号`・`分割数`・`文字数`・`本文` |
| 評価ログ | `日時`・`実行ID`・`実行キー`・`結果ID`・`回`・`種類`・`ステップ`・`モデル`・`プロンプトのハッシュ`・`呼び出し`・`分割番号`・`分割数`・`HTTPの状態`・`所要時間ms`・`停止理由`・`トークン数`・`エラー`・`リクエスト`・`応答` |

### 10.2 1 回の評価

1. Actions の「SHAMAN | n8n Workflow実行」で `test` を選び、`test:` の入力欄（ステップ・KEYWORD・OPTION1・SITE_ID・入力の結果ID・基準の結果ID・モデル・回数）を書いて実行する（[RUN_FROM_ACTIONS.md](RUN_FROM_ACTIONS.md)）。既定の値のまま実行すると、P1 を 1 回動かす。
   - Workflow が、入力の値で「評価の実行」に待機中の行を足してから（`Eval: New Run Row`・`Eval: Add Run`。実行キーは `actions-<Actions の実行 ID>-<n8n の実行 ID>`）、**その行だけ**を実行する。前からある待機中の行（手で書いた行など）は使わず、そのまま残す。
   - 足した行の値が不正（KEYWORD が無いなど）で止めたときは、その行を「エラー」にし、メモに理由を書く（`Eval: Stop Has Row?` → `Eval: Mark Failed`）。待機中のまま残さない。
   - n8n の画面の「Execute workflow」から実行するときは、行を足さない。「評価の実行」に待機中の行を 1 行書いておく（ステップ・入力・必要ならモデル・回数・基準の結果ID、状態 `待機中`）。
2. 画面から実行するときは、待機中の行を 1 件だけにする。2 件以上あれば、`Eval: Pick Run` が止める。
3. 「評価の実行」の行の状態が「完了」（または「エラーあり」「エラー」）になり、結果ID の列に結果 ID が並ぶ。測定値は「評価結果」、出力の全文は「評価データ」、呼び出しの記録は「評価ログ」で見る。
4. 次のステップを評価するときは、手順 1 の入力の結果ID に、前のステップの結果 ID を書く。
5. 本番の実行が途中のステップで止まったときは、`eval_input_execution` にその実行 ID を書き、止まったステップを選んで実行する（§4.3）。

例：P4 のモデルを替えて比べる。P3 の結果 `R120-1` を入力にして、モデルの列を空（今の本番のモデル）で 1 回、新しいモデルで 1 回実行し、前者の結果 ID を後者の基準の結果ID に書く。

### 10.3 失敗したとき

- 「評価の実行」の行が「エラー」になったときは、メモの列と「評価ログ」の停止の行に理由がある。行を直して、状態を `待機中` に戻せば、もう一度実行できる。
- 回の途中の失敗は、その回だけが評価結果の「エラー」になる。Parse が失敗した回（`max_tokens`・`refusal` など）の評価データには `_meta` だけが残り、モデルの生の出力は「評価ログ」の応答の列に残る（同じ結果 ID）。
- シートへの書き込みが 3 回とも失敗すると、実行は失敗し、「評価の実行」の行は「処理中」のまま残る（n8n の Error Trigger は、手動の実行では動かない）。n8n の実行の一覧でエラーを確かめ、行の状態を `エラー` にしてから、やり直す。それまでに書けた回の結果は、評価結果に残っている。

## 11. 実機でまだ確かめていないこと

- Google Sheets ノード（v4.5）の読み込みの絞り込み（`filtersUI`）が、一致した行をすべて返すこと（n8n のソースでは、v4.5 の既定は「すべて返す」）。
- 長い本文（45,000 文字）を RAW で書いて読み直したとき、1 文字も変わらないこと（Workflow は文字数を照合し、違えば入力に使わずに止める）。
- Loop Over Items（v3）に Code ノードの出力を戻したとき、終わりの出力に、すべての回の結果が出ること。
- n8n の実行時間の上限（P4 を 5 回続けると、30 分を超えることがある）。
- HTTP Request ノードの通信エラー（タイムアウトなど）の item の形（`error` が文字列かオブジェクトか）。どちらでも内容を残すようにしてある。
